Estimating the Dominant Eigenvalue from Compliance Telemetry

A method note. How to estimate $\lambda_1$ for a security programme from telemetry a compliance pipeline already emits, and what the estimate is worth.

This is the methods companion to Being in the Loop. That essay argues that systems near a threshold announce themselves, and that nobody gets to watch from outside. This note is the arithmetic: what to measure, how to fit it, and where the fit stops being trustworthy. The essay can be read without it. It cannot be checked without it.

On the worked example. The telemetry here comes from the continuous-compliance pipeline that publishes this site's own machine-readable artifacts. That pipeline is real and it runs on every deploy, but it carries no federal data and it has no agency sponsor. It demonstrates a mechanism; it is not an authorized system, and nothing below should be read as a claim that a control has been assessed by anyone other than me. The state vector is a worked example, not an attestation.

Two limits inherited from the essay, stated once here rather than repeated throughout. Every estimator below assumes the Jacobian holds still over the estimation window, and a security programme that senses its own boundary does not hold still. And every mean-based summary of a heavy-tailed quantity describes its outliers. Both are reasons to distrust the number in exactly the situation you most want it.

1. A state space for a security programme

1.1 Security State Space

Represent the security state as a vector with components for vulnerability state (count, severity, exploitability), configuration drift from baseline, exposure or attack surface, analyst attention and fatigue, and response capacity. Additional components can be added; these are the ones that reliably move.

Note that analyst attention is a state variable, not a parameter. That is the whole difference between this model and a conventional risk model, and everything interesting follows from it.

1.2 Evolution Equation

The state evolves under three influences: internal dynamics (automated processes, natural drift, attention decay), threat forcing (attacker activity, new CVEs), and development forcing (deployments, changes). For stability analysis we absorb the time-averaged forcing into the equilibrium condition and treat deviations as perturbations.

That absorption is a real assumption and it is doing more work than it looks like. It requires the forcing to be roughly stationary over the estimation window. An adversary who adapts to your defenses is not stationary forcing, which is one reason the Jacobian problem below matters.

1.3 Equilibria and the Jacobian

Multiple equilibria may exist: a secure attractor where detection outpaces exploitation and remediation outpaces introduction, and a compromised attractor where the system drifts toward breach. The Jacobian at an equilibrium encodes how each state variable responds to changes in every other one.

In plain language: each entry answers a question like "if the vulnerability count goes up by one, how fast does configuration drift change?" The matrix is a complete map of how every variable influences every other, evaluated at the current steady state. The eigenvalue conditions from the essay then apply directly: a negative real eigenvalue means an alert spike triggers a response and the system returns to normal. A positive one means alert fatigue spirals: more alerts, less attention, more missed alerts, more alerts. Complex eigenvalues with negative real part describe oscillating remediation cycles that eventually settle; complex with positive real part describes escalating boom-bust.

1.4 Security Bifurcations

Bifurcation Security Manifestation
Saddle-node Staffing drops below minimum; the secure equilibrium vanishes
Transcritical Alert volume crosses threshold; triage quality inverts
Hopf System begins oscillating between alert flood and calm
Pitchfork Security posture splits into "good team" / "bad team" modes

The saddle-node is the most operationally relevant, and it is the one in the 3 a.m. scenario. In the one-dimensional reduction $dx/dt = \mu - x^2$, the parameter $\mu$ is remediation capacity minus vulnerability introduction rate. When $\mu$ crosses zero the secure equilibrium does not degrade. It ceases to exist. There is no warning in the state variable itself, only in how it recovers.

1.5 What the method does, needs, and outputs

FedRAMP 20x mandates deterministic telemetry and persistent validation, which means a compliance pipeline now emits the kind of uniformly-sampled time series that eigenvalue estimation needs. This is a new opportunity: continuous monitoring data was designed to answer "are you compliant today," and it happens to also answer "how fast do you recover," which is a much harder question and a more useful one.

What the method does. Take seven observable Key Security Indicators: open vulnerabilities, critical findings, configuration drift, remediation queue depth, response capacity, patch compliance, and asset telemetry coverage: sampled daily. Fit a model that predicts tomorrow's vector from today's. The eigenvalues of the fitted coefficient matrix say whether the system returns to equilibrium after a disturbance and how fast. Convert those to continuous time and the dominant one is $\lambda_1$.

What it needs. Roughly ten observations per variable for the autoregressive fit, so about seventy days of daily data for a seven-component vector; two weeks after a perturbation for the response method; ninety days for reliable trend detection in the slowing-down indicators.

What it outputs. A dominant eigenvalue with a sign and a magnitude: negative and large means a comfortable stability margin, negative and near zero means the margin has gone, positive means the system is diverging and the only question is when. Plus the off-diagonal structure, which says which subsystems are coupled: usually the more actionable result, because coupling is something you can go and cut.

The full method: the estimator, the algorithm, the data sources, the sampling requirements, the detection rules for critical slowing down, and the back-testing procedure: is in section 2. It is a methods paper, and keeping it out of the argument is the whole point of this page.1

One warning belongs up front. Everything in section 2 estimates a Jacobian from history and assumes it still applies, and the essay's closing argument is about why that assumption fails hardest in exactly the situations you built the estimator for.

1.6 Multi-Threshold Cascade Analysis

Real environments have several thresholds operating semi-independently: alert volume, staffing, vulnerability accumulation, configuration drift. Each is a condition where some subsystem's dominant eigenvalue approaches zero.

They are coupled, which means crossing one shifts the effective parameters of the others. A cascade occurs when that shift is enough to push a neighbouring subsystem across its own threshold. In practice: an alert volume spike produces analyst fatigue, which produces missed vulnerabilities, which pushes vulnerability accumulation across its threshold, which produces the compromise. Each step is small and each step is legible only in retrospect.

This is the mechanism Woods calls decompensation: a system that absorbs a challenge, then absorbs the next one with less margin, then falls over, and the fall looks sudden from outside even though the capacity was draining the entire time.

1.7 Control Implications

Control theory provides tools for eigenvalue placement: designing feedback to shift eigenvalues leftward, increasing the stability margin. For security operations that means strengthening negative feedback (faster detection-response loops), weakening positive feedback (breaking alert-fatigue spirals), and increasing damping (reducing oscillation).

Desired Eigenvalue Shift Operational Implementation
More negative real part Faster recovery, automation, reduced queue depth
Reduced imaginary part Smoother workflows, reduced boom-bust cycles
Increased stability margin Capacity buffer, redundancy, cross-training

Observability: can we infer system state from available measurements? Telemetry gaps create unobservable modes: eigenvalues we cannot detect. Controllability: can we influence all state variables? Uncontrollable modes, such as threat actor behavior, must be treated as forcing functions, not state variables.

Note the tension with the drift argument above. Eigenvalue placement says: buy margin. The law of stretched systems says: any margin you buy will be spent on new demand unless something actively protects it. Both are true, which means the control problem is not technical.

1.8 Worked Example: Two Variables, One Number

The smallest model that shows the real behavior has two variables: $V$, the open vulnerability count, and $R$, effective response capacity. Four things happen. Vulnerabilities arrive at rate $\alpha$. They get remediated, but the remediation saturates: when the queue is short, more vulnerabilities means proportionally more fixed; when the queue is long, each additional one gets less attention and the total rate flattens out. Vulnerabilities also decay on their own as the environment rotates. And capacity drains: every open vulnerability consumes some analyst attention, so a growing queue directly reduces the capacity available to shrink it.

That last coupling is where the failure comes from. It is a positive feedback loop between workload and incapacity, and it is why the failure is a cliff, not a slope.2

The result. With plausible default parameters, the model undergoes a saddle-node bifurcation at

$$\alpha_c \approx 6.09 \text{ vulnerabilities per day.}$$

Below that rate, a stable equilibrium exists, perturbations decay, and recovery time scales as $1/|\lambda_1|$. As $\alpha$ climbs toward 6.09, the equilibrium still exists but $\lambda_1 \to 0^-$: recovery slows, variance grows, autocorrelation approaches 1. Above 6.09 there is no equilibrium at all. Vulnerabilities accumulate, capacity drains, and the feedback between them accelerates the divergence.

In plain language: there is an arrival rate above which this team cannot exist in a steady state, not "performs badly," but has no steady state to be in. And the number is not large. Six vulnerabilities a day is an unremarkable Tuesday. The interesting operational fact is that the team at $\alpha = 5.5$ and the team at $\alpha = 6.5$ look almost identical on any static dashboard, and are in completely different dynamical regimes.

I want to be clear about what this number is and is not. It is a property of a two-equation toy with parameters I chose to be plausible. It is not a measurement of anything, and 6.09 is not a threshold anyone should adopt. What is transferable is the shape: saturating response plus capacity drain gives you a saddle-node, and a saddle-node gives you a cliff with critical slowing down in front of it. The deflationary theorem in the essay is the reason the shape transfers and the specific number does not.

2. Estimating $\lambda_1$ from the telemetry

Section 1.5 says what the estimate is for. This section is how to compute it.

Read the essay on why MTTR fails first. The single most important decision here is which estimator you use. The perturbation-response method is a direct measurement; everything else is an inference from a summary statistic, and summary statistics of heavy-tailed operational data are treacherous. Order of preference: perturbation-response, then autoregressive fit, then the slowing-down indicators, then variance amplification. Do not build a composite index out of means.

2.1 The KSI state vector

FedRAMP 20x mandates deterministic telemetry and persistent validation, which yields uniformly sampled time series. Define the observable state vector:

$$\mathbf{K}(t) = \begin{pmatrix} V_{\text{open}}(t) \\ V_{\text{critical}}(t) \\ C_{\text{drift}}(t) \\ Q_{\text{depth}}(t) \\ R_{\text{capacity}}(t) \\ P_{\text{compliance}}(t) \\ A_{\text{coverage}}(t) \end{pmatrix}$$

Component Meaning Data source
$V_{\text{open}}$ Count of open vulnerabilities Vulnerability scanner exports
$V_{\text{critical}}$ Critical/high severity findings Filtered scanner data (CVSS ≥ 7.0)
$C_{\text{drift}}$ Configuration drift (% deviation from baseline) Configuration management delta reports
$Q_{\text{depth}}$ Remediation queue depth Ticketing system query
$R_{\text{capacity}}$ Available response capacity (FTEs × efficiency) Staffing records × utilization
$P_{\text{compliance}}$ Patch compliance rate (% systems current) Patch management reports
$A_{\text{coverage}}$ Asset coverage ratio (% assets with telemetry) Asset inventory vs. telemetry coverage

Recommended sampling: daily snapshots for all components, weekly aggregates for trend analysis, monthly rolling windows for eigenvalue estimation.

Minimum data requirements: autoregressive estimation needs $N \geq 10d$ observations, so 70+ days for a 7-component vector; perturbation-response needs 14+ days post-perturbation; slowing-down detection needs 90+ days for reliable trend detection.

2.2 Perturbation-response method (preferred)

This method exploits natural experiments: known perturbations followed by measurable recovery. Suitable events include a major CVE disclosure affecting the environment, a significant deployment or infrastructure change, an analyst departure or addition, a tool outage and restoration, or an audit finding requiring remediation.

Step 1. At time $t_0$, identify a perturbation $\delta\mathbf{K}$: a vulnerability spike, a queue surge, with a known magnitude.

Step 2. Track the deviation from the pre-perturbation baseline: $\Delta K_i(t) = K_i(t) - K_i^{\text{baseline}}$.

Step 3. For a stable system the deviation decays exponentially, $\Delta K_i(t) \approx \Delta K_i(t_0) e^{\lambda_1 (t - t_0)}$. Fit by log-linear regression:

$$\ln|\Delta K_i(t)| = \ln|\Delta K_i(t_0)| + \lambda_1 (t - t_0)$$

The slope is $\lambda_1$ directly.

Step 4. If multiple components are perturbed, the full recovery decomposes over modes, $\Delta\mathbf{K}(t) = \sum_i c_i \mathbf{v}_i e^{\lambda_i (t - t_0)}$, and principal component analysis of the recovery trajectory separates them.

Why this one is preferred: it never pools across incident classes. Each event carries its own magnitude and its own recovery curve, so the heavy-tail problem that destroys mean-based metrics does not arise. Report the resulting $\lambda_1$ estimates as a distribution across events, by quantile, not as an average.

2.3 Autoregressive estimation

Step 1. Collect $N$ observations at uniform intervals $\Delta t$ and standardize each component to zero mean and unit variance: $\tilde{K}_i(t) = (K_i(t) - \bar{K}_i)/\sigma_{K_i}$.

Step 2. Fit the first-order model $\tilde{\mathbf{K}}(t + \Delta t) = A \tilde{\mathbf{K}}(t) + \boldsymbol{\epsilon}(t)$ by ordinary least squares:

$$\hat{A} = \left( \sum_{t=1}^{N-1} \tilde{\mathbf{K}}(t+1) \tilde{\mathbf{K}}(t)^T \right) \left( \sum_{t=1}^{N-1} \tilde{\mathbf{K}}(t) \tilde{\mathbf{K}}(t)^T \right)^{-1}$$

Step 3. Compute the eigenvalues $\{\mu_i\}$ of $\hat{A}$ from $\det(\hat{A} - \mu I) = 0$.

Step 4. Convert to continuous time: $\lambda_i = \ln(\mu_i)/\Delta t$. For complex $\mu_i = r e^{i\theta}$, $\lambda_i = \ln(r)/\Delta t + i\theta/\Delta t$.

Stability criterion: System is stable if $|\mu_i| < 1$ for all $i$ (equivalently, $\text{Re}(\lambda_i) < 0$).

In plain language: the model treats tomorrow's metrics as a weighted combination of today's plus noise. The weights form a matrix, and the eigenvalues of that matrix say whether the system is stable (all inside the unit circle) or drifting toward instability (any approaching the boundary). The discrete-to-continuous conversion translates "multiplied each day" into "growing or shrinking per unit time."

ALGORITHM: Eigenvalue_Estimation_From_KSI

INPUT:
  K[1..N, 1..d]  -- N observations of d KSIs
  dt             -- sampling interval (days)

OUTPUT:
  lambda[1..d]   -- continuous-time eigenvalues
  stability      -- boolean stability assessment
  margin         -- distance to instability

PROCEDURE:
  1. Standardize data:
     FOR i = 1 TO d:
       mean[i] = MEAN(K[*, i])
       std[i] = STDEV(K[*, i])
       K_tilde[*, i] = (K[*, i] - mean[i]) / std[i]

  2. Construct design matrices:
     Y = K_tilde[2..N, *]           -- (N-1) x d matrix
     X = K_tilde[1..N-1, *]         -- (N-1) x d matrix

  3. Estimate coefficient matrix:
     A = (Y^T * X) * INVERSE(X^T * X)

  4. Compute eigenvalues of A:
     mu[1..d] = EIGENVALUES(A)

  5. Convert to continuous-time:
     FOR i = 1 TO d:
       lambda[i] = LOG(mu[i]) / dt

  6. Assess stability:
     max_real = MAX(REAL(lambda[*]))
     stability = (max_real < 0)
     margin = -max_real

  7. RETURN lambda, stability, margin

2.4 Critical slowing down detection (model-free)

These work without fitting an explicit model, which is what makes them deployable, and it is the approach van Beers et al. used for real-time monitoring on hardware.

Method 1: lag-1 autocorrelation. $\rho_1 = \text{Cov}(K(t), K(t + \Delta t))/\text{Var}(K(t))$. For an AR(1) process $\rho_1 \approx e^{\lambda_1 \Delta t}$, so $\rho_1 \to 1$ as $\lambda_1 \to 0^-$. Compute in rolling windows (30 days is a reasonable default); rising $\rho_1$ signals threshold proximity.

Method 2: variance amplification. Near threshold $\sigma^2 \propto \sigma^2_{\text{forcing}}/(2|\lambda_1|)$. Track the coefficient of variation in rolling windows, controlling for changes in the mean.

Method 3: detrended fluctuation analysis. Compute the cumulative deviation $Y(t) = \sum_{s \leq t} (K(s) - \bar{K})$, divide into windows of size $n$, detrend each window, and compute the RMS fluctuation $F(n)$. The scaling exponent $\alpha$ from $F(n) \propto n^\alpha$ indicates white noise at $\alpha = 0.5$, persistent correlations above it, and strong persistence approaching $\alpha \to 1$.

Scope, carried forward from the essay: all three detect bifurcation-induced tipping under slow forcing. Rate-induced and noise-induced tipping need different instruments, and so does the case where the eigenvalue driving the failure is not the one driving the observed fluctuations.

2.5 Jacobian structure from cross-correlations

The off-diagonal elements encode coupling between KSIs, and in practice this is the more actionable output: coupling is something you can go and cut.

Compute the cross-correlation matrix $C_{ij}(\tau) = \text{Corr}(K_i(t), K_j(t + \tau))$. Contemporaneous correlation $C_{ij}(0)$ indicates shared forcing or fast coupling; lagged correlation at $\tau > 0$ suggests $K_i$ influences future $K_j$. A Granger causality test, whether past values of $K_i$ improve prediction of $K_j$ beyond $K_j$'s own history, gives evidence that $J_{ji} \neq 0$.

Granger causality is predictive precedence, not causation, and in a system where both variables respond to an unmeasured third the test will happily report a coupling that does not exist. Treat the results as hypotheses about structure, to be checked against how the work actually happens.

2.6 Interpretation and calibration

Eigenvalue Condition Operational Meaning Recommended Action
All $\text{Re}(\lambda_i) < -0.1$ Strong stability margin Monitor; maintain current processes
Dominant $-0.1 < \text{Re}(\lambda_1) < 0$ Reduced stability margin Increase monitoring frequency; review capacity
$\text{Re}(\lambda_1) \approx 0$ Threshold proximity Immediate intervention; add capacity; reduce load
$\text{Re}(\lambda_1) > 0$ Unstable; diverging Emergency response; stop non-critical changes; surge capacity
Complex eigenvalues, $\text{Im}(\lambda) \neq 0$ Oscillatory dynamics Identify feedback delays; smooth batch processes
Large off-diagonal $|J_{ij}|$ Strong coupling Monitor upstream system; consider decoupling

The numerical boundaries above are placeholders pending calibration against a specific environment. They are not thresholds anyone should adopt as given; $\lambda_1$ has units of inverse time, so the meaning of $-0.1$ depends entirely on the sampling interval and the domain's natural timescale.

Back-testing. Identify historical threshold crossings (major incidents, prolonged degradation), compute eigenvalue estimates for the periods leading up to them, check whether $\lambda_1 \to 0$ actually preceded the crossing, and calibrate warning thresholds against the lead time you need. Test robustness against different window sizes, first- versus second-order models, missing data, and outliers.

Ground truth validation. Where possible, compare eigenvalue-based predictions to actual incident rates, audit findings, red team/penetration test results, and known staffing or tooling degradation periods.

And the limit on all of it. Every method here estimates a Jacobian from history and assumes it still applies. The essay explains why that assumption fails hardest in the near-threshold regime these methods exist to detect. Back-testing partially conceals this problem instead of solving it: a historical crossing is an episode in which the organization was reorganizing, so a model fitted across it is fitted across several different vector fields. Good back-test performance is weaker evidence than it appears.

2.7 Reference implementation

A Python implementation of the two-variable model in 1.8 and its seven-dimensional extension is available on request. It demonstrates eigenvalue estimation from synthetic time series, critical slowing down detection, and early warning behavior: on synthetic data, where the generating process is known and the Jacobian genuinely is fixed. That is the right place to validate an estimator and the wrong place to conclude anything about real operations.

  2. The two-variable model in full.

    State variables: $V$ (open vulnerability count) and $R$ (effective response capacity, in FTEs).

    $$\frac{dV}{dt} = \alpha - \frac{\beta R V}{V + K_v} - \eta V \qquad \frac{dR}{dt} = \gamma(R_0 - R) - \delta V$$

    $\alpha$ is the vulnerability introduction rate and the bifurcation parameter. The term $\beta R V/(V + K_v)$ is saturating remediation in Michaelis–Menten form: linear in $V$ at low load, saturating at $\beta R$ at high load, with $K_v$ the half-saturation constant. $\eta V$ is natural decay from environment rotation and upstream patching. $\gamma(R_0 - R)$ is capacity recovery toward baseline $R_0$. $\delta V$ is capacity drain, each open vulnerability consumes attention.

    Why not Lotka–Volterra. The classical predator-prey form has $\det(J) = 0$ at its coexistence equilibrium, giving a centre rather than a stable node or spiral: marginal stability as a structural artifact rather than as a finding. It also has no saddle-node, so the stable state shifts under stress instead of vanishing. Saturating remediation and linear capacity drain fix both.

    Equilibrium. $dR/dt = 0$ gives $R^* = R_0 - \delta V^*/\gamma$. Substituting into $dV/dt = 0$:

    $$\alpha = \frac{\beta(R_0 - \delta V^*/\gamma)V^*}{V^* + K_v} + \eta V^*$$

    which is nonlinear in $V^*$ with no closed form.

    Jacobian. With $J_{11} = -\beta R^* K_v/(V^* + K_v)^2 - \eta$ and $J_{12} = -\beta V^*/(V^* + K_v)$:

    $$J = \begin{pmatrix} J_{11} & J_{12} \\ -\delta & -\gamma \end{pmatrix}$$

    $$\text{tr}(J) = J_{11} - \gamma < 0 \qquad \det(J) = \gamma\left(\frac{\beta R^* K_v}{(V^* + K_v)^2} + \eta\right) + \frac{\delta \beta V^*}{V^* + K_v} > 0$$

    Both determinant terms are positive whenever $R^* > 0$, so the equilibrium has genuine asymptotic stability. Eigenvalues are $\lambda_{1,2} = \left(\text{tr}(J) \pm \sqrt{\text{tr}(J)^2 - 4\det(J)}\right)/2$.

    Bifurcation. As $\alpha \to \alpha_c$ the stable node and a saddle collide and annihilate; at the collision $\det(J) = 0$ and $\lambda_1 = 0$. There is no closed form for $\alpha_c$, but it is located numerically as the $\alpha$ at which $\max(\text{Re}(\lambda_i)) = 0$. With $\beta = 0.5$, $K_v = 80$, $\eta = 0.01$, $\gamma = 0.2$, $R_0 = 15$, $\delta = 0.005$: $\alpha_c \approx 6.09$ vulnerabilities per day.

    Status of that number. It is a property of this toy at these parameters, and the parameters were chosen to be plausible rather than measured. The deflationary theorem in the essay is the reason the qualitative shape transfers and the number does not.↩︎
