There are two defensible endings and the task is to pick one, not to split the difference:

**A — delete them.** The remote-state backend has been live since Task 16 and state is durable in S3 with versioning; the honest recovery story for a lost state file is "restore the S3 object version", not "re-adopt 30 resources by hand". If that is the story, write it into `docs/recovery-plan.md` step 2 (which currently says a plain `make pipeline` suffices when state is intact, and says nothing about state being *lost*), then delete the 297 lines and the `REBUILD_STATE` variable.

**B — keep them and make them honest.** Fix the three stale "ephemeral state" comments, add a note above `REBUILD_STATE` recording when the path was last exercised, and accept that a 297-line untested branch sits in the hottest file in the repo.

A is better unless there is a recovery scenario S3 object versioning genuinely does not cover — a bucket-level deletion, or recovering into a *different* account, which is exactly the case `docs/recovery-plan.md` already contemplates ("recovering into a new account"). If that case is real, the import steps are the implementation of it and option B is the answer; then the recovery plan should say so and reference them by name, which today it does not.
