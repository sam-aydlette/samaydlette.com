# CM — Configuration Management

Configuration management is GitOps. Every change to infrastructure or content reaches `main` through a commit that triggers the OPA gate, the Terraform plan, the apply, the canonical inventory build, the Sigstore signing, and the publish. Changes reach `main` through pull requests; branch protection requires the status checks, `scn-tag` among them, to pass. The PR description is the change request and carries the significant-change evaluation; the merge is the approval.

The **Significant Change Notification (SCN) evaluation** is explicit on every change (`SCN-CSO-EVA`). Each pull request description (or direct-push commit message) carries an `SCN-Type:` line (`not-significant`, `routine-recurring`, `adaptive`, `transformative`, `emergency` or `class-change`), a one-line `SCN-Rationale:`, and for adaptive, transformative and emergency changes the `SCN-Record:` that will document it. The required `scn-tag` check fails a change without them; there is no default. `class-change` always fails: a change of certification class is a new certification and needs a new assessment. A transformative change cannot merge until its initial plan has been published for 30 business days and its final plan for 10. The format and one example per type are in [`docs/scn/evaluation-examples.md`](../scn/evaluation-examples.md); emergency changes follow [`docs/incident-response.md`](../incident-response.md). Each deploy appends every merged evaluation to the signed, append-only evaluation log at `/.well-known/scn-evaluations.json` (`SCN-CSO-MAR`). Adaptive and transformative changes get a row in [`docs/scn/scn-register.csv`](../scn/scn-register.csv) and a record with the security impact analysis; each deploy publishes them in FedRAMP's SCN schema with an Atom feed, which is how notice is given (`SCN-CSO-NOM`, `SCN-CSO-HIS`, `SCN-CSO-HRM`). A scheduled check fails on any record or notice past its deadline. See [`docs/scn/README.md`](../scn/README.md).

The canonical inventory at `/.well-known/ksi-signal.json` is the authoritative system inventory (CM-8 family). It is generated automatically from Terraform state, Lambda package locks, and content hashes — see [`docs/ksi-signal.md`](../ksi-signal.md). Each component carries a normalized identifier (PURL/ARN/SHA-256/HBOM ref), a security category (per FIPS 199), and an information-flow tag (per `MAS-CSO-FLO`).

**20x rule integration.** Significant Change Notifications (full SCN-* family — `SCN-CSO-MAR`/`INF`/`HIS`/`HRM`/`ARI`/`NOM`/`EMG`/`EVA` plus the Adaptive/Routine-Recurring/Transformative tier rules. Transformative changes carry five notification windows: 30 business days before starting (initial plans, `SCN-TRF-NIP`), 10 before starting (final plans, `SCN-TRF-NFP`), 5 after finishing (`SCN-TRF-NAF`), 5 after the verification/validation completes (`SCN-TRF-NAV`), and updated service documentation within 30 (`SCN-TRF-UPD`); a recognized-assessor human-validation review (`SCN-TRF-TPR`) is a SHOULD. Minimum Assessment Scope (`MAS-CSO-IIR`/`FLO`/`TPR`; third-party AWS resources documented at the inheritance level per `MAS-CSO-TPR`). `MAS-CSO-MDI` (federal-customer-data metadata) is **N/A** — its `MAS-CSO-IIR` trigger does not fire with no federal customer data held — and `MAS-CSO-SUP` (supplemental, non-offering materials) carries nothing for this system. KSI-CMT (Change Management).

**Review cadence.** Continuous; effectiveness review monthly via the no-out-of-band-commits check on `main`.
