# CM — Configuration Management

Configuration management is GitOps. Every change to infrastructure or content reaches `main` through a pull request; `main` is protected, requires a pull request (administrators included) and requires the `scn-tag` check. Merging triggers the OPA gate, the Terraform plan, the human-approved apply, the canonical inventory build, the Sigstore signing, and the publish. The pull request description is the change request and carries the security impact analysis; the review, the approval and the merge commit are the audit record.

The **Significant Change Notification (SCN) category** of every change is decided by a **security impact analysis** (`SCN-CSO-EVA`). The pull request description answers the yes/no questions in [`data/sia-questions.json`](../../data/sia-questions.json), adapted from the security impact analysis template in NIST SP 800-128, in an `SIA:` block. On every pull request into `main`, [`scripts/sia.py`](../../scripts/sia.py) (the `scn-tag` step "Validate the SCN evaluation") reads the diff: a question whose triggers it touches must be answered, and a "no" must give a reason. The type follows `SCN-CSO-EVA`'s order: a FIPS 199 or certification class change fails the check (it needs a new assessment); otherwise any transformative "yes" makes it **Transformative**, any adaptive "yes" makes it **Adaptive**; with every answer "no", a declared recurring category (`dependency-update`, `vulnerability-remediation`, `evidence-refresh`) makes it **Routine Recurring**, a change that touches no security-relevant path is **Not Significant**, and anything else is **Adaptive**. The `SCN-Type:` line must equal the result; it may be left out only for Routine Recurring and Not Significant. `SCN-Type: emergency` is reserved for emergency changes per `SCN-CSO-EMG` (see [`docs/incident-response.md`](../incident-response.md) for procedures and retroactive-documentation requirements). A Dependabot pull request that only changes versions is answered automatically as `dependency-update`. Audit records of these evaluations are the pull requests and their check runs (`SCN-CSO-MAR`). Adaptive and Transformative changes additionally get a durable, structured record in [`docs/scn/`](../scn/): a per-change SCN record carrying the `SCN-CSO-INF` fields plus a copy of the SIA, and a row in the machine-and-human-readable register [`docs/scn/scn-register.csv`](../scn/scn-register.csv) (`SCN-CSO-HRM`), retained for at least 12 months (`SCN-CSO-HIS`).

The canonical inventory at `/.well-known/ksi-signal.json` is the authoritative system inventory (CM-8 family). It is generated automatically from Terraform state, Lambda package locks, and content hashes — see [`docs/ksi-signal.md`](../ksi-signal.md). Each component carries a normalized identifier (PURL/ARN/SHA-256/HBOM ref), a security category (per FIPS 199), and an information-flow tag (per `MAS-CSO-FLO`).

**20x rule integration.** Significant Change Notifications (full SCN-* family — `SCN-CSO-MAR`/`INF`/`HIS`/`HRM`/`ARI`/`NOM`/`EMG`/`EVA` plus the Adaptive/Routine-Recurring/Transformative tier rules. Transformative changes carry five notification windows: 30 business days before starting (initial plans, `SCN-TRF-NIP`), 10 before starting (final plans, `SCN-TRF-NFP`), 5 after finishing (`SCN-TRF-NAF`), 5 after the verification/validation completes (`SCN-TRF-NAV`), and updated service documentation within 30 (`SCN-TRF-UPD`); a recognized-assessor human-validation review (`SCN-TRF-TPR`) is a SHOULD. Minimum Assessment Scope (`MAS-CSO-IIR`/`FLO`/`TPR`; third-party AWS resources documented at the inheritance level per `MAS-CSO-TPR`). `MAS-CSO-MDI` (federal-customer-data metadata) is **N/A** — its `MAS-CSO-IIR` trigger does not fire with no federal customer data held — and `MAS-CSO-SUP` (supplemental, non-offering materials) carries nothing for this system. KSI-CMT (Change Management).

**Review cadence.** Continuous; effectiveness review monthly via the no-out-of-band-commits check on `main`.
